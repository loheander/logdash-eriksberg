# Dark mode for the dashboard

Status: proposed

## Where things stand

A light/dark toggle already exists, so this plan closes the gaps rather than building the feature.

- `app/shell.py`: `dcc.Store("theme", storage_type="local")`, a `◐` toggle button, and a callback that sets `MantineProvider.forceColorScheme` from the store.
- `app/figures.py`: `template(scheme)` gives Plotly light and dark palettes; every analysis figure takes `scheme` and every page callback has `Input(THEME_STORE_ID, "data")`.
- Tests cover `next_theme`, `template`, and the two theme callbacks (`tests/unit/test_app.py`, `tests/unit/test_figures.py`).

## Gaps found

1. **Explorer grid is never themed.** `dag.AgGrid` in `analyses/explorer.py` has no theme setting and stays light in dark mode. This is the most visible defect.
2. **Flash of light theme on load.** `MantineProvider` starts with `defaultColorScheme=LIGHT, forceColorScheme=LIGHT`. A returning dark-mode user sees light until the store callback fires.
3. **No OS preference.** First visit always starts light; `prefers-color-scheme` is ignored.
4. **Hard-coded colours in figures.** `add_note` uses `#868e96` regardless of scheme. Check the same for `hosts.py`, `anomalies.py`, `temporal.py` (burst and gap shading, annotations).
5. **Colour scales on dark backgrounds.** `Blues` (features association heatmap) fades to near-white at the low end, which glares on a dark page. `RdBu_r`, `Viridis` need a visual check. Hover labels and colourbar text may also need template settings.
6. **Toggle affordance.** A bare `◐` glyph with no label or tooltip, and it does not show which mode is active.
7. **Pages with no theme input.** Confirm every figure callback, including `explorer` and any static figure in `hosts.py`, re-renders on toggle. Pages that cache figures (the `features.py` docstring mentions memoisation) must keep the scheme out of the cache key, or recompute cheaply.

## Plan

### 0. Centralise theming in `app/theme.py`

This applies [ADR001](../adrs/ADR001-central-switches-have-central-code.md): a switch that is central in the UI has one central representation in the code.

Theme code is scattered today: the store id, toggle and `next_theme` live in `shell.py`; `LIGHT`, `DARK`, `scheme_name`, the palettes and `template`/`style` live in `figures.py`; and eight analysis modules import `THEME_STORE_ID` from `shell.py`, which makes the analyses depend on the shell. Every new themed component would add another place to touch. Create one module, `src/logdash/app/theme.py`, as the only place that knows about colour schemes. Do this first; later steps build on it.

`theme.py` owns:

- **Constants:** `LIGHT`, `DARK`, `THEME_STORE_ID`, `PROVIDER_ID`, `THEME_TOGGLE_ID`.
- **Scheme logic:** `scheme_name`, `next_theme`.
- **One palette table per scheme** (a frozen dataclass or dict) holding every colour the app uses: text, muted/note text, grid, background, hover label, sequential scale, diverging scale, and the AG Grid theme name. No colour literals outside this table. `PALETTE` (the categorical colourway) moves here too, since it is a theme value.
- **Plotly:** `template(scheme)` and `style(fig, scheme, **layout)`; `empty_figure` and `add_note` stay in `figures.py` but take their colours from `theme`.
- **Component helpers:** `provider_props(scheme)` for `MantineProvider`, `grid_class(scheme)` (or the AG Grid theme option) for `dag.AgGrid`, and `toggle()` that builds the header control.
- **Wiring:** `theme_store()` returns the `dcc.Store`; `theme_input()` returns `Input(THEME_STORE_ID, "data")` so pages do not spell the id; `register_theme_callbacks(app)` holds the toggle callback, the provider callback, the grid callback and the OS-preference clientside callback.

Changes elsewhere:

- `shell.py` loses its theme code and calls `theme.theme_store()`, `theme.toggle()` and `theme.register_theme_callbacks(app)`; `register_shell_callbacks` keeps only the filter callback.
- `figures.py` keeps the non-theme helpers (`lttb`, `top_n_other`, binning, `shorten_middle`) and no longer defines `LIGHT`, `DARK`, `_SCHEMES`, `template` or `style`. Callers import from `theme` directly; no re-exports, so there is one import path.
- Each analysis replaces `from logdash.app.shell import THEME_STORE_ID` and `Input(THEME_STORE_ID, "data")` with `theme.theme_input()`, and `figures.style(...)` with `theme.style(...)`. Analyses then depend on `theme`, not on `shell`.
- Add a guard test: grep the `src/logdash` tree and fail if a colour literal (`#rrggbb`, `rgba(`) appears outside `theme.py`, and if `THEME_STORE_ID` is referenced outside `theme.py`.

### 1. Explorer grid
- Use `theme.grid_class(scheme)` on `dag.AgGrid`: `ag-theme-alpine` / `ag-theme-alpine-dark`, or the equivalent for the installed AG Grid 35 theming API (check whether `dashGridOptions={"theme": ...}` replaced class-based themes in v33+, and use whichever the installed `dash-ag-grid` supports). The choice stays inside `theme.py`.
- The grid callback registered in `register_theme_callbacks` sets the grid's class or theme option from the store. Explorer's own callbacks stay unchanged, so a toggle does not refetch rows.

### 2. Initial scheme and no flash
- Make `MantineProvider` default to `"auto"` (`defaultColorScheme="auto"`) and drop the hard `forceColorScheme=LIGHT`; set `forceColorScheme` only once the user has picked explicitly.
- Initial store value: `None` (follow the OS) instead of `LIGHT`. `scheme_name(None)` already maps to light for figures; add a small clientside callback reading `matchMedia("(prefers-color-scheme: dark)")` so figures and grid follow the OS when no explicit choice exists.
- Verify with a hard reload with local storage set to `dark`: the first paint should be dark, or at worst a single frame.

### 3. Figure colours
- Add `note` and `muted` colours to the palette table in `theme.py`; make `add_note` take `scheme` (callers already have it) and replace the literal.
- Grep each analysis for literal colours (`#`, `rgba`, `"white"`, `"black"`, `"grey"`) and route them through `theme` (palette table or `PALETTE`). The guard test from step 0 keeps this true.
- Set `hoverlabel`, `colorbar` text, and `legend` font in the template if the check in step 5 shows contrast problems.

### 4. Colour scales
- Add a per-scheme sequential scale to the `theme.py` palette table, exposed as `theme.sequential(scheme)` (for example `Blues` in light, a dark-friendly scale such as `Viridis` or reversed `Blues` in dark) and use it in `features.association_figure` and `temporal` host heatmap.
- Keep `RdBu_r` for the diverging correlation matrix if it reads well on dark; confirm by eye.

### 5. Toggle control
- Build the control in `theme.toggle()` so the header only places it. Replace `◐` with a sun/moon icon (`dash_iconify` is not a dependency; use `dmc.Tooltip` plus text label "Light"/"Dark", or a `dmc.SegmentedControl` in the header, to avoid a new dependency).
- Add an accessible label (`aria-label`) and show the active scheme.

### 6. Tests
- Move the theme tests (`next_theme`, `template`, the two theme callbacks) into a new `tests/unit/test_theme.py` and update imports.
- `test_figures.py`: assert `add_note` and the scale helper differ by scheme; assert no figure helper emits a literal light-only colour when `scheme="dark"` (iterate over figures built from fixtures and scan `fig.to_dict()` for the old literals).
- `test_app.py`: layout test that the explorer grid gets the dark class when the store is `dark`; layout test for the `auto` provider default.
- Keep the 90 % coverage gate; run `ruff check`, `ruff format --check`, `mypy src`.

### 7. Manual check (screenshots)
Run `uv run logdash serve` and, for every page (home, overview, distributions, temporal, templates, explorer, features, pca, anomalies, hosts), toggle to dark and check:
- text and axis contrast, annotations, legends, hover labels, colourbars;
- tables (`dmc.Table`, link tables), date picker popover, multi-select dropdowns;
- the explorer grid, including header, selected row, tooltip.
Refresh the README screenshots if they show light mode only.

## Order and size

0. Centralise into `theme.py` (a pure refactor with no behaviour change; existing tests must pass unchanged apart from imports).
1. Explorer grid theming (small, highest value).
2. Figure literals and colour scales (small).
3. Initial scheme and OS preference (medium; needs a clientside callback).
4. Toggle control (small).
5. Tests and screenshot pass (alongside each step).

Ship step 0 as its own PR so the move is reviewable on its own, then steps 1–2, then 3–4.

## Open questions

- Should the choice follow the OS until the user clicks the toggle, or always default to light as today?
- Is a new dependency (`dash-iconify`) acceptable for the toggle icon, or should the control stay text-only?
- Does the installed `dash-ag-grid` 35.3 use class-based themes or the new JS theming API? This decides the shape of step 1 and needs a short spike.
